# Architecture Decision Records

## ADR-1. Clean-архитектура с MVI вместо MVVM

**Контекст.** В вакансии допускаются MVVM и MVI. Продукт — realtime-экран со списком,
фильтрами, офлайн-очередью и потоком событий с сервера.

**Решение.** MVI: sealed-классы событий, одно неизменяемое состояние, `Bloc` как
редьюсер. MVVM с `ChangeNotifier`/`StateFlow` на таком количестве источников (кэш + WS +
счётчик очереди) быстро приводит к «расползанию» состояния по полям.

**Следствия.**
- `+` состояние воспроизводимо и логируется целиком, тесты сравнивают состояния;
- `+` нет промежуточных «полувалидных» состояний;
- `−` больше кода на событие; компенсируется sealed-классами и exhaustive switch.

## ADR-2. Hive без `TypeAdapter`: JSON-снимки в боксе

**Контекст.** Нужен быстрый офлайн-кэш нарядов и очередь мутаций.

**Решение.** Храним `Map<String, dynamic>` (тот же JSON, что отдаёт API) по ключу `order.id`.
Адаптеры и `hive_generator` не используем.

**Следствия.**
- `+` один формат для сети и кэша: нет дублирования моделей и расхождений при миграции;
- `+` нет codegen-зависимости в хранилище;
- `−` нет типобезопасности на уровне бокса — компенсируется DTO с защитным парсингом
  (`OrderDto.fromJson` терпит мусор, см. тесты);
- `−` при росте схемы понадобится версионирование ключей (`orders_cache_v2`) — имя бокса
  уже содержит версию.

## ADR-3. Единая точка записи в кэш (кэш как source of truth)

**Контекст.** REST-ответ и WS-событие могут описывать один наряд и приходить в произвольном
порядке.

**Решение.** UI читает только `watchCachedOrders()`. И REST, и WS пишут в кэш через репозиторий.

**Следствия.**
- `+` нет конфликтов «кто последний»: последовательность записей однозначна;
- `+` офлайн и онлайн-режимы используют один код отображения;
- `−` запись в Hive на каждое WS-событие — приемлемо при 50 событиях/мин, при больших
  объёмах нужен батчинг.

## ADR-4. Список нарядов — не через Retrofit

**Контекст.** Retrofit парсит ответ на главном изоляте. Список нарядов — самая тяжёлая
операция (до 300 КБ JSON).

**Решение.** `GET /orders` читаем как строку (`ApiClient.getJson<String>`) и парсим в
изоляте (`PayloadDecoder`), остальные вызовы — типизированный Retrofit.

**Следствия.**
- `+` нет просадки кадров при обновлении списка;
- `−` два способа работы с одним API; компенсируется тем, что список — единственное место
  с такой нагрузкой, и это явно задокументировано.

## ADR-5. Idempotency-Key на клиенте

**Контекст.** Обрыв связи на этапе ответа приводит к повтору мутации.

**Решение.** Каждая мутация получает `newRequestId()`; заголовок `Idempotency-Key`
передаётся и в первом запросе, и в ретраях, и при отправке из outbox.

**Следствия.**
- `+` сервер может безопасно отбрасывать дубликаты;
- `+` `RetryInterceptor` не ретраит POST без ключа (явное правило в коде);
- `−` требуется поддержка на бэкенде (описана в контракте).

## ADR-6. Биометрия как локальный замок, а не замена токену

**Контекст.** Требование — нативные функции, включая биометрию; данные наряда должны
быть недоступны при передаче телефона коллеге.

**Решение.** `local_auth` используется как локальный шлюз: сессия Firebase живёт отдельно,
биометрия лишь снимает UI-замок (`AppLockBloc`). Замок включается при уходе в фон и
настраивается в `SettingsStore`.

**Следствия.**
- `+` Face ID/Touch ID не блокируют работу, если биометрия не настроена;
- `+` тесты блока не требуют устройства (сервис замокан);
- `−` это не криптографическая защита данных; для неё нужен ключ в Keychain/Keystore и
  шифрование кэша (roadmap).

## ADR-7. Firebase опционален на этапе запуска

**Контекст.** Портфолио-проект должен открываться у ревьюера без выдачи ключей и
`google-services.json`.

**Решение.** `bootstrap` ловит ошибку `Firebase.initializeApp()` и поднимает приложение с
`DemoAuthRepository`, без push и Crashlytics; данные — из Hive.

**Следствия.**
- `+` проект запускается «из коробки», UI и офлайн-сценарии доступны;
- `+` в продакшне деградация тоже корректна: приложение не падает при сбое инициализации;
- `−` в демо-режиме нет реального Auth — это видно в `README` и в коде DI.
